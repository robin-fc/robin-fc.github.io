# 兰心实验室

本来是上半年做的一些ai相关的产品尝试，扔了不管怪可惜的，所以稍微改了改界面，做了一个整体的入口。取名完全是因为 lancy.site 域名便宜，正好谐音兰心，致敬一下我老婆。

> 关键词：个人网站

## 1. 介绍

lancy.site是一个梳理我个人探索ai相关应用的门户平台，只是结合threejs稍微设计了一下界面跟交互：以「数字星球」为隐喻，入口 [lancy.site](https://lancy.site) 上，每一个项目都以坐标标记的形式分布在同一个球面上；点击坐标，可以看到项目的快照与简介，这不仅仅是一个作品集——它是我对「AI 能做什么」「我能在 AI 边上走多远」这个问题的持续回答。此外我在上海标记了坐标，可以进入四个3D场景，每个场景我都设置了一面墙来放作品网站的截图，点击可以引导打开新网站。

### 设计动机：为什么是一颗星球？

大多数作品集网站用的是网格或卡片列表，平铺、规整、安全。  
我想要一种更强的空间感：每个项目不是「条目」，而是星图上的一个点。  
选中某个点后，信息面板从右侧滑入，背景中是那颗缓慢自转的地球——这种体验更接近探索，而不是浏览。

```text
[ 星球 ] ── 拖拽旋转 / 滚轮缩放 / 选择坐标
              │
              ▼
        [ 信息面板 ]  →  进入项目链接
```

隐喻本身也在服务内容：这里的所有工具都处于「生长」状态，不是一次性交付后就不再更新。  
`ACTIVE LABS` 的计数器始终在记录当前的项目数量，而不是最终完成数。

### 技术栈总览

整个站点由以下层构成：

| 层级     | 技术                                         | 说明                                 |
| -------- | -------------------------------------------- | ------------------------------------ |
| 3D 场景  | [Three.js](https://threejs.org/) (ES Module) | 地球几何体、光照、纹理贴图、射线拾取 |
| 核心逻辑 | 原生 JavaScript (ESM)                        | 星球交互、标记定位、状态机           |
| 视觉样式 | 手写 CSS + CSS Variables                     | HUD / Cyberpunk 风格深色主题         |
| SEO 结构 | JSON-LD Schema                               | `WebSite` + `ItemList` 结构化数据    |
| 子项目   | Next.js / 静态 HTML                          | 各项目独立仓库，独立部署             |

### 星球渲染管线

四个 JS 文件承担主要职责：

```
app.js      ← 入口：DOM 初始化、事件绑定、全局状态
planet.js   ← Three.js 场景：光照、几何体、纹理、动画循环
gallery.js  ← 艺廊视图：WASD 移动、碰撞检测、展品交互
projects.js ← 纯数据：项目元信息、坐标映射、能力标签
```

**渲染循环的核心**：用 `requestAnimationFrame` 驱动地球的自转与鼠标拖拽的同步，同时把 3D 世界坐标投影到屏幕空间，实时更新每个标记按钮的 `top/left` 位置。

### 进入艺廊：从星球坐标到 3D 漫游

#### Portal 过渡机制

点击底部「SHANGHAI / ENTER THE ARCHIVE」按钮后，系统并不直接跳入艺廊，而是先触发一段精心编排的状态迁移：

```
idle → portal → portal-blackout → gallery-loading → gallery-reveal → gallery
```

关键巧思有两处：

1. **黑色帧遮挡切换**：在切换到艺廊前，先将星球渲染器的背景设为纯黑（`setClearColor(0x000000, 0)`），利用这一帧视觉断点隐藏 renderer 之间的切换过程，再重新淡入艺廊场景。用户感知到的是一段「穿越」而非页面刷新。

2. **预加载并行化**：在点击 portal 的同时，四个 3D 房间模型就已经通过 `Promise.all()` 开始并行下载——`room_diorama_model.glb`、`art_gallery.glb`、`round_floor_baked.glb`、`dining_room__kichen_baked.glb`。进度条分三个阶段显示状态：「建立空间连接」「载入艺术空间」「唤醒空间角色」，让等待变成叙事的一部分。

#### 场景切换（Scene Switching）

所有房间在同一时刻都加载进场景，切换时仅靠 `room.visible = false/true` 切换可见性，完全避免二次加载。切换流程：

```javascript
// 隐藏旧场景中的展板
this.frameGroups.forEach((group) => this.scene.remove(group));
// 前进到下一个场景索引
this.currentSceneIndex = (this.currentSceneIndex + 1) % 4;
// 切换可见性
Object.entries(this.rooms).forEach(([name, room]) => {
  room.visible = name === nextSceneName;
});
// 重建当前房间的展板位置
this.createProjectFrames();
```

每次切换后，展板会自动按当前房间的墙壁边界重新布局，而不是固定坐标。

#### 玩家移动与相机控制

**键盘 WASD**：监听 `keydown/keyup` 维护一个 `Set` 追踪当前按下键，每帧根据组合状态计算速度向量，叠加方向旋转后推进相机位置。Shift 激活慢跑模式（对应不同的骨骼动画）。

**鼠标环视**：拖动时捕获指针位移量，映射为相机的俯仰角（pitch）和偏航角（yaw），采用球面坐标系而非欧拉角，避免万向节死锁。

**移动端**：出现虚拟摇杆（`#mobile-stick`），将触点偏移量归一化为 `[−1, 1] × [−1, 1]` 的二维向量，替代 WASD；右下角新增「RUN」按钮作为慢跑切换开关。

**轮播缩放**：鼠标滚轮调整相机距离（最近 2.55m，最远 4.15m），超出范围则 clamp 防止穿墙。

## 2.复盘：建模与适配的弱项

回头看这个项目，有几个明显的短板值得记录，以便以后有空改进。

**模型比例不统一，下载的免费商用的，过大影响网页加载速度**  
四间房来自不同来源，各自单位尺度、原点和朝向都不一样。目前的做法是用 `normalizeModel()` 强行统一高度后再手工调整位置，每一间都需要单独调 `position` 和 `scaleMultiplier`，几乎没有自动化手段。如果后续增加新场景，这一步会非常耗时且容易出错。

**碰撞检测过于简单**  
AABB 盒子的方案对矩形房间勉强够用，但无法处理斜坡、阶梯或不规则地形——玩家在正确的位置会直接穿模或撞墙。理想情况是用地面法线做投影碰撞，或者引入轻量级物理引擎（如 cannon-es）。

**资源加载毫无优先级**  
四个房间模型一次性全部下载，最小的 5MB，最大的超过 25MB。首屏加载时间完全取决于最大那个，且没有分块加载或懒加载策略。对于移动端来说这个体积负担明显过重，应该按场景按需加载。

**展板和相机的硬编码间距**  
展板位置目前是基于 `size.x * 0.12` 这类经验系数推算的，在不同房型下表现不一致。有些房间里展板离墙太远或贴得太近，缺乏对墙面几何的主动识别——应该读取墙面法线来动态决定展板朝向和距离。

**模型 LOD 缺失**  
手机和桌面使用同一套完整精度的模型，没有任何细节层次调整。高分辨率贴图在低带宽设备上尤其沉重。真实情况应准备两套尺寸（高/低 poly）并根据设备性能动态切换。

**地球模型的加载路径冗余**  
星球视图和艺廊视图共享一个 WebGL Renderer，但在切换时有轻微闪烁——原因是 renderer 的 clear color 和 tone mapping exposure 需要在两个场景之间分别管理，目前靠黑色帧硬遮，不够优雅。更好的做法是为两个视图各自持有独立的 renderer 实例，并通过 Canvas swap 平滑过渡。

## 3.结语

整体来说这个网站我个人对于构思跟web版本的实现还是比较满意的，做出了一个比较亮眼的个人作品展示门户。只是建模跟性能优化上还需打磨。
